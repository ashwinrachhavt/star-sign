## 2026-10-25 — Consent state model: connections + flows (ASH-256)

- Change: New `connections` table (0006) implementing the two-person consent state machine: requested → accepted (recipient-only), revoked (either party, from requested or accepted), disconnected (from accepted only); terminal states irreversible. Enforcement is IN THE DATABASE — a before-update trigger validates both the transition and the acting party (auth.uid()); handlers only map violations to 409. Partial unique index blocks duplicate active pairs in either direction. RLS fail-closed: participants SELECT their own rows; INSERT by requester only as 'requested'; UPDATE participant-scoped (trigger still gates); no DELETE policy, no anon policies. `connection_state_log` audits every transition with actor. Route handlers per 0.3: POST /api/connections, GET/DELETE /api/connections/{id}, PUT /api/connections/{id}/acceptance, PUT /api/connections/{id}/declination.
- Migration: 0006_connections.sql
- Rollback: drop connection_state_log + connections (header comment has the statements).
- Risk: acceptance/decline handlers race with concurrent state changes → the trigger rejects, handler maps to 409 (documented; no lost-update path since trigger rechecks inside the statement). Chart-data visibility (5.2) is NOT granted by this table — deliberately; this ticket only owns the consent state machine.
- Decisions: (1) decline and withdraw both land in `revoked` (with actor recorded in the log) — a distinct `declined` state was rejected as it leaks nothing but complicates the machine; api.md's four states kept. (2) DELETE on accepted → `disconnected`, DELETE on requested → `revoked`; both immediate, unilateral, idempotent (204 on repeat). (3) Harness shim gained `grant usage on schema auth` (Supabase parity — trigger functions calling auth.uid() outside pure RLS context need it). (4) Found and fixed during development: the first trigger draft allowed requester self-acceptance — caught by probe test, now "only the recipient can accept" is DB-enforced.
- Deletion interplay (0.1c note): connection rows cascade on profile deletion (FK on delete cascade) and the state log records history; when account deletion (ASH-231) lands it should rely on the cascade plus export of this log. No code needed here.
