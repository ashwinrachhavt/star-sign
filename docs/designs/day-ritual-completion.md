## Problem Statement

The /day screen is the product's core loop (product.md: "Individual chart + daily ritual comes before connections and compatibility"), yet it is the least-finished surface. Code inspection found:

1. **Life Areas show a hardcoded dash.** `rankLifeAreas()` (packages/core/src/ruleset.ts:124) computes real hot/warm/quiet temperatures from summed transit scores, but `reading.ts:212` keeps only `ranked.slice(0, 3).map(r => r.area)` — the temperature is discarded before persistence. The UI (apps/web/app/day/page.tsx:140, apps/mobile/src/app/day.tsx:146) renders `state="—"`. FR-03 requires hot/warm/quiet. The data exists; the product throws it away.
2. **No reflection capture from a reading.** FR-08: "save a prompt or write a private note from a reading." The reflections API and table exist (POST /api/reflections, unique per user+date), the You/Saved tab lists them — but /day has no affordance to write one. The loop reading → reflection is broken.
3. **No past-day navigation.** daily_readings persists history (one canonical row per user+date), but /day only ever shows today. Co-star's day screen pages back through days.
4. **No cross-links.** The reference product links placements to people ("Add friends to see who's similar"); ours has no link from day or placement cards to People.
5. **Mobile parity.** apps/mobile/src/app/day.tsx has the same dash bug and no reflection or day navigation; mobile has no You screen at all (stack: day, week, connections only).

## What Makes This Cool

The honest-dash problem is the interesting one: the engine already knows today is a "hot" money day versus a "quiet" one, and that single word changes how the whole reading lands. Surfacing it costs almost nothing because the computation exists — this is a "complete the circuit" feature, not a new one. The reflection loop turns a consumption screen into a practice: read the sky, write one line, come back tomorrow to your own words next to the same sky.

## Constraints

- Copy discipline: .agents/copy.md — life areas stay monochrome caps words; hot/warm/quiet, never percentages. Template/copy changes bump COPY_VERSION.
- Uncertainty contract: houses never shown for approximate/unknown birth times; day navigation must not imply readings can be regenerated for past dates (canonical persisted rows only).
- Design system v1: hairline cards, three type voices, no accent colors; LifeAreaRow already matches the LifeAreaRow component spec.
- No new dependencies; no schema change needed for temperatures (life_areas is jsonb) — payload shape change only.
- Entitlement gate: splitReadingForTier runs server-side; new day-screen content must respect it.

## Premises

1. The day ritual is the product's core loop; /day is the least-finished surface. — user agreed (screenshot + "Add these sections now")

## Recommended Approach

Approach C, in four PR-able steps (one ticket each, per workflows.md):

1. **ASH-268 (proposed): Persist and render life-area temperatures.**
   - packages/core/src/reading.ts: keep the ranked entries — `lifeAreas: ranked.slice(0,3)` (area + temperature; score stays internal to the ruleset, never in the persisted payload).
   - Old rows (string-array life_areas): parse tolerantly at read time and render "—" for those rows only; no migration (provenance honesty — decided).
   - Bump COPY_VERSION (payload shape changed; readings persist provenance versions).
   - apps/web/app/day/page.tsx + apps/mobile/src/app/day.tsx: pass `temperature` to LifeAreaRow; copy.md-compliant display ("HOT", "WARM", "QUIET").
   - Tier behavior: hot/warm/quiet is free content (Co-star keeps the day-at-a-glance free; product.md §11 keeps the daily ritual free). splitReadingForTier passes life_areas through untouched — add a gate test asserting temperatures survive the free-tier split.
   - Tests: temperature determinism, quiet-day behavior (fewer areas, honest), backward-compatible parse of old rows, entitlement-gate passthrough.
2. **ASH-269 (proposed): Reflection capture from the day screen.**
   - Web: client component on /day — "Save a reflection" text affordance under the reading; POST /api/reflections with forDate = today; 409 → "already saved" honest state with link to /you/saved. This note-writing affordance is the FR-08 fulfillment (the "write a private note" disjunct; prompt-saving stays out of scope).
   - Mobile: same via existing api lib (add saveReflection calling POST /api/reflections).
   - Tier behavior: reflections are the user's own private content — free, never gated (FR-08: no unconsented personalization; deletion/export already covered).
   - Copy: new UI strings are copy.md-governed (voice table: empty/offline register); they are UI affordances, not interpretation templates — no COPY_VERSION bump (that tracks interpretation text only).
   - Tests: UI-level happy path + 409 path; gate test — reflection affordance and saved reflections fully reachable on the free tier.
3. **ASH-270 (proposed): Day navigation over persisted readings.**
   - /day?date=YYYY-MM-DD reads the canonical row; absent → honest "no reading for this day" (never generate for past dates — generation stays today-only per reading contract).
   - Prev/next mono-caps links; today bounds the forward direction.
   - Tier behavior: past readings the user already earned stay free to re-read (architecture.md: saved readings are durable records, not cache); no gate.
   - Copy: nav labels are UI affordances — no COPY_VERSION bump.
   - Mobile parity: same query params.
   - Tests: absent-day honest state, forward bound at today, date not generated; gate test — past-day reads fully served on the free tier.
4. **ASH-271 (proposed): Cross-links + mobile You screen.**
   - Day screen footer: "☰ Add friends to see who's similar →" linking /people (copy.md consent tone).
   - Placement cards on /you link to /people similarly.
   - Mobile: the day footer link ships in v1 (trivial); placement-card cross-links land with the mobile You screen in the same ticket — the mobile You screen ships as the full RN chart grid (proposal adopted; open question resolved), mirroring web /you.
   - Tier behavior: cross-links are navigation — free, no gate.
   - Copy: footer string is copy.md-governed UI copy — no COPY_VERSION bump.
   - Tests: gate test — day footer link and You-screen cross-links render and navigate on the free tier; mobile You grid renders all 10 placements + ascendant for exact time, omission path for non-exact.

## Open Questions

None — all product calls in this doc are decided: old rows render "—"; mobile You screen ships the full RN chart grid (ASH-271); score stays internal; note-writing is the FR-08 fulfillment.

## Success Criteria

- /day shows hot/warm/quiet for every life area on a fresh reading; no hardcoded dash anywhere. Old readings render "—" for life areas only.
- A user can save a reflection from /day and see it in /you/saved.
- A user can view yesterday's reading (persisted row) and cannot trigger generation for a past date.
- Cross-links work: the day-screen footer link reaches /people, and /you placement-card links are present and functional.
- Mobile day matches web behavior for all of the above (temperatures, reflection save, day navigation, day footer cross-link); mobile has a You surface with the full chart grid and placement-card cross-links.
- Entitlement gate: temperatures, reflections, history, and cross-links are all free-tier content — a gate test per step asserts nothing gated leaks and nothing free is withheld.
- pnpm typecheck / test / build green; copy changes carry COPY_VERSION bump (ASH-268 only; UI affordance strings are copy.md-governed but don't bump it).

## Chat direction: specialized astronomy agents (owner request, mid-session)

The owner wants the chat experience delivered by "eve agents" — specialized agents with astronomy-specific knowledge, harness-oriented for the user, rather than one general chatbot. This extends Ask Star Sign (ASH-266), which is currently a bounded template-based Q&A over stored chart facts. Direction: evolve it into a small set of scoped agents (e.g. natal-chart explainer, transit watcher, relationship-synastry reader), each grounded in the same stored-facts retrieval layer, under the same FR-09 acceptance rules (never invent placements, decline prediction requests). Architecture and provider choices are a separate design conversation — noted here so the ASH-266 foundation is read as the base layer, not the end state.
